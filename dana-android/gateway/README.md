# مرصاد آنلاین — راه‌اندازی توسط مالک سرویس

**مسیر کاربر:** «ورود با ایمیل» ← دریافت کد شش‌رقمی ← انتخاب مدل از فهرست حساب ← مرور متن و ارسال. ساخت تصویر هم از همان حساب استفاده می‌کند. در «فرمان»، کارهای محلی بدون حساب انجام می‌شوند و برای فهمِ آنلاینِ یک متن تأیید جداگانه لازم است. پاسخ مدل فقط یک پیشنهاد است؛ به‌خودی‌خود تنظیمی را تغییر نمی‌دهد.

**این پوشه سرویس مستقر یا اشتراک فعال نیست.** یک حساب مرصاد تنها به مدل‌هایی دسترسی می‌دهد که مالک سرویس آزمایش و فعال کرده است؛ نه به همهٔ مدل‌ها و نه به حساب یا اشتراک شخصیِ سرویس‌دهنده‌ها. کاربر نباید کلید، آدرس سرور یا حساب جداگانه وارد کند. مراحل زیر فقط برای مالک سرویس‌اند.

## ۱. احراز هویت و دسترسی

- یک پروژهٔ **Supabase hosted** با تأیید اجباری ایمیل و OTP شش‌رقمی بسازید. در هر دو قالب **Confirm signup** و **Magic Link** مقدار `{{ .Token }}` را به‌صورت کد قرار دهید ([راهنمای قالب و SMTP](../docs/05-studio-fa.md#راهاندازی-برای-مالک-برنامه)). از SMTP تراکنشیِ دامنهٔ تأییدشده، نرخ ارسال/تأیید محدود و زمانی کوتاه برای اعتبار کد استفاده کنید. گذرواژهٔ SMTP در Supabase می‌ماند.
- در شبکهٔ آزمایشیِ محدود، `MRSAD_PUBLIC_SIGNUP=false` و `MRSAD_MEMBER_IDS` برابر شناسه‌های UUID کاربران مجاز در Supabase باشد. دریافت و تأیید کد با داشتن سهمیه یا مجوز استفاده از مدل یکی نیست. برای آزمون عمومی روی پروژهٔ واقعی ابتدا کنترل سوءاستفاده و بودجه، شرایط استفاده، حریم خصوصی و مسیر حذف حساب/داده را آماده کنید. APK فعلاً چالش CAPTCHA سمت ورود ندارد؛ بدون راه‌حل سازگار آن را به ثبت‌نام عمومی تبدیل نکنید.
- `MRSAD_AUTH_ORIGIN` آدرس دقیق `https://<project-ref>.supabase.co` و `MRSAD_AUTH_PUBLISHABLE_KEY` فقط `sb_publishable_…` است. از کلید `service_role`، کلید `sb_secret_…` یا راز JWT استفاده نکنید. در هر درخواست فهرست و مدل، دروازه هویت را با `/auth/v1/user` همان پروژه تأیید می‌کند و فقط حساب ایمیلی تأییدشده و مجاز را می‌پذیرد.

## ۲. فهرست و بودجهٔ مدل‌ها

- از `.env.example` یک فایل خصوصی بسازید و آن را در Git نگذارید. `MRSAD_TEXT_MODELS` فهرست JSON حداکثر ۳۰ شناسهٔ دقیق OpenRouter با `id`، `title` و `provider` است. پیش از فعال‌کردن هر مدل، شناسهٔ جاری، کیفیت پاسخ فارسی، هزینه، شرایط استفاده، پشتیبانی پارامترها و دسترسی منطقه‌ای را با حساب واقعی خودتان بررسی کنید. مدل خودکار یا جایگزینی بی‌اجازه فعال نمی‌شود. `MRSAD_PLANNER_MODEL` اختیاری است؛ مدل انتخابی باید در فهرست متن باشد و خروجی JSON آزموده‌شده بدهد.
- `MRSAD_IMAGE_MODELS` فهرست جداشده با ویرگول از مسیرهای `openai-sunburst`، `avalai-sunburst` یا `gemini-pro` است. سقف پاسخ تصویر ۸ MiB است. «High» و «2K» کیفیت *درخواستی*‌اند، نه نتیجهٔ تضمین‌شده. تنها مسیرهایی را فعال کنید که با کلید و بودجهٔ حساب مالکتان آزموده‌اید. شناسهٔ یک مدل موجود را به سرویس دیگری تخصیص ندهید.
- کلیدهای مدل فقط در محیط سرور یا secret manager قرار می‌گیرند. پیش‌فرض ۱۲ واحد برای هر حساب و ۱۰۰ واحد برای کل سرویس در هر روز UTC است؛ گفتگو و فهم فرمان ۱ واحد، تصویر ۵ واحد. این واحدها معادل قیمت پولی نیستند. برای هر کلید سقف واقعیِ هزینه، هشدار و امکان توقف اضطراری نزد ارائه‌دهنده نیز بگذارید.
- پیش از درخواست بالادستی، مصرف و شناسهٔ یکتای درخواست در یک تراکنش SQLite رزرو می‌شود. خطای سرویس یا توقف انتظار ممکن است سهمیه را مصرف کند؛ هیچ POST مدل خودکار تکرار نمی‌شود. SQLite فقط UUID حساب و درخواست، روز و مصرف را دارد (بدون متن، تصویر، ایمیل یا توکن). حذف رکوردهای قدیمی هنگام رزرو انجام می‌شود. متن/تصویر از دروازه عبور می‌کند و سرورِ مدل می‌تواند آن را تابع سیاست خودش نگه دارد؛ ادعای «نگهداری صفر» نکنید.

## ۳. سرویس HTTPS و APK

از پوشهٔ `dana-android/gateway` در سرور مالک:

```sh
docker build -t mrsad-gateway .
docker volume create mrsad-usage
docker run -d --name mrsad-gateway --restart unless-stopped \
  --env-file /secure/path/mrsad.env \
  --mount source=mrsad-usage,target=/data \
  -p 127.0.0.1:8080:8080 mrsad-gateway
```

حجم `/data` باید برای UID `10001` قابل‌نوشتن باشد و در بازاستقرار باقی بماند. یک نمونهٔ سرویس با یک دیسک پایدار اجرا کنید؛ چند نمونه با SQLite جداگانه یک سهمیهٔ مشترک نمی‌سازند. یک دامنهٔ HTTPS با گواهی معتبر جلوی این پورت بگذارید. پراکسی نباید هدر `Authorization`، متن یا پاسخ‌ها را لاگ یا cache کند، POST را تکرار کند یا به دامنهٔ دیگر ریدایرکت کند. برای رد درخواست‌های بزرگ، سقف بدنه را ۴۸ KiB و برای تصویر تایم‌اوت پراکسی را حداقل ۱۳۵ ثانیه در نظر بگیرید. `GET /healthz` فقط آمادگی فرایند است؛ اثبات OTP یا مدل نیست.

در محیط ساخت APK (یا **Actions → Variables** برای بیلد آزمایشی Lite) فقط این سه مقدار عمومی قرار می‌گیرند:

| متغیر | مقدار |
|---|---|
| `DANA_EMAIL_PROJECT_URL` | همان `MRSAD_AUTH_ORIGIN` |
| `DANA_EMAIL_PUBLISHABLE_KEY` | همان کلید عمومی `sb_publishable_…` |
| `DANA_GATEWAY_URL` | یک مبدأ HTTPS بدون مسیر، پورت اختصاصی، اطلاعات ورود یا query |

در `dana-android` دستور `./gradlew :app:assembleCompatDebug` APK آزمایشی Android 8+ را می‌سازد؛ برای ساخت در Actions، workflow **mrsad Android compatibility** را از شاخهٔ فعال با `managed: true` اجرا کنید. اجرای معمول CI عمداً به سرویس آنلاین وصل نیست، اجرای pilot خودکار انتشار عمومی ندارد. برای توزیع واقعی، از کلید انتشار پایدار خودتان استفاده کنید؛ APK دیباگ تست به‌روزرسانی امضاشدهٔ نصب قبلی نیست.

## قبل از توزیع

1. از خود APK روی دستگاه واقعی، با ایمیل واقعیِ مجاز یک کد بگیرید؛ بعد از تأیید یک درخواستِ گفتگو و (اگر فعال است) یک تصویر بفرستید، بدون تنظیم اضافه یا حساب دوم. بستن و بازکردن و خروج از حساب و دریافت کد جدید را امتحان کنید. یک حساب نامجاز باید رد شود.
2. مدل، کیفیت و مقصدِ مرورشده، سهمیه‌ پس از ارسال، خطای کمبود اعتبار و توقف را با صورت‌حساب و تنظیم ارائه‌دهنده تطبیق دهید. شبکه و منطقهٔ کاربران را آزمایش کنید؛ فعال‌شدن رله دسترسی منطقه‌ای یا شرایط ارائه‌دهنده را تغییر نمی‌دهد.
3. فرمان، ساعت، تنظیمات وای‌فای، انتخاب/رد نقش دستیار و دسترس‌پذیری تشخیص گفتار فارسی را روی یک گوشی Android 8+ و دستگاه جدیدتر آزمایش کنید. محدودیت‌های OEM و وجود برنامهٔ ساعت/سرویس گفتار را در نظر بگیرید.

آزمون‌های رله با `python -m unittest discover -s tests -v` در محیط `requirements.txt` اجرا می‌شوند. CI ایمیل، GoTrue و SMTP محلی را به همین کد رله متصل می‌کند؛ ارائه‌دهنده‌های مدل در این آزمون‌ها شبیه‌سازی می‌شوند. هیچ‌یک تحویل ایمیل عمومی، پرداخت، کیفیت مدل واقعی یا رفتار یک گوشی مشخص را ثابت نمی‌کند.
