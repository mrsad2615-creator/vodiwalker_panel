## 4. Video Player Audit

### 4.1 The audio-with-no-image defect — root cause

This is the defect you reported, and the source shows why.

`ui/video/VideoPlayer.kt:276-290`:

```kotlin
factory = { ctx ->
    PlayerView(ctx).apply {
        useController = false
        setShowBuffering(PlayerView.SHOW_BUFFERING_NEVER)
        resizeMode = AspectRatioFrameLayout.RESIZE_MODE_FIT
        player = controller.player     // ← set once, in the factory
    }
},
update = { view ->
    view.resizeMode = if (fillScreen) { ... } else { ... }   // ← player never touched
},
```

And `data/PlayerController.kt:194-205`:

```kotlin
@Composable
fun rememberPlayerController(uri: String): PlayerController {
    val controller = remember(uri) { PlayerController(context, uri) }   // ← new controller per uri
    DisposableEffect(controller) { onDispose { controller.release() } }  // ← old one released
    ...
}
```

**The chain:**
1. The viewer selects a different clip → `uri` changes.
2. `remember(uri)` builds a **new** `PlayerController`, which builds a **new** `ExoPlayer`.
3. `DisposableEffect` **releases the old** `ExoPlayer`.
4. `AndroidView`'s `factory` does **not** re-run, because the `AndroidView` node is not recreated — only `update` runs.
5. `update` sets `resizeMode` and leaves `view.player` pointing at the **released** player.
6. `PlayerView` attached to a released player draws nothing. The new player still has an audio track and plays it.

Result: **sound from the new player, picture from a dead one.** This is exactly what was reported. **VERIFIED by code; not reproduced on hardware.**

Severity: **critical**. Every clip after the first in a session is audio-only.

### 4.2 Formats and codecs

ExoPlayer defaults are used; no custom renderers, no `DefaultMediaSourceFactory` configuration. Supported formats are therefore whatever the device's MediaCodec exposes. Fixtures are H.264/AAC MP4. **PARTIALLY VERIFIED** — two short clips only; no HEVC, VP9, AV1, HDR, 10-bit, variable frame rate, or rotation metadata has ever been tried.

### 4.3 Buffering and errors

`setShowBuffering(SHOW_BUFFERING_NEVER)` plus a custom spinner driven by `PlayerState.isBuffering`. On error, `PlayerStatusOverlay` shows a message. Error recovery is a manual retry; there is no exponential backoff and no automatic retry. **PARTIALLY VERIFIED.**

### 4.4 What a Huawei-grade player would add

Listed as opportunities only, not commitments:

| Capability | Current | Gain |
|---|---|---|
| Vertical drag on the right half = volume | absent | The gesture every video app has |
| Vertical drag on the left half = brightness | absent | Same |
| Horizontal drag = seek (already present) | present | — |
| Lock button that disables all touch except unlock | absent | Stops accidental taps on a phone held at an angle |
| Prev/next buttons around play | absent | Reaching clip 2 of 40 currently means opening the filmstrip |
| Playback continues when the screen is off / app backgrounded | absent | Requires a `MediaSessionService` + foreground service; this is the one item that materially changes the architecture |
| Frame-accurate seek preview (thumbnail while scrubbing) | absent | Expensive; needs a decoder pool |
| Speed menu without leaving the player | present | — |

Two of these are cheap (volume/brightness gestures, lock). One is expensive (background playback). None requires network.

## 6. Visual Design Audit

### 6.1 Colour (`ui/theme/HgTheme.kt:29-60`, `Palette.kt`)

A role-based palette, not raw colours: `background`, `surface`, `surfaceHigh`, `surfaceSunken`, `textPrimary/Secondary/Tertiary`, `textOnMedia`, `accent`, `accentMuted`, `onAccent`, `accentWarm`, `divider`, `scrim`, `danger`, `favourite`. Light and dark sets exist. Documented contrast floor: 4.5:1 body, 3:1 icons.

**Weakness:** light `background = #F7F7F9` and `surface = #FFFFFF` differ by about 3% luminance. On a phone in daylight this is nearly invisible, so the "tonal surface" argument in the file's own KDoc does not hold at typical brightness. **VERIFIED by reading the values.**

### 6.2 Typography (`ui/theme/HgTypography.kt`)

Inter (variable) with Vazirmatn as fallback in one `FontFamily`. Line-height is trimmed per size. Named styles for count label, album title, timecode, player indicators.

**Weakness:** the fallback works by glyph coverage, so a Persian string inside an English sentence will render in Vazirmatn while its neighbours are Inter — correct, but the two have different x-heights and it shows in mixed strings such as "8 photos and 2 videos" translated as «۸ عکس و ۲ ویدیو». **PARTIALLY VERIFIED** — visible in the Persian build only, which no screenshot covers.

### 6.3 Icons (`ui/icons/HgIcons.kt`)

34 hand-drawn vectors: 24 dp box, 1.8 dp stroke, round caps. Deliberately lighter than Material's 2 dp.

**Weakness:** `material-icons-extended` is still a dependency (`app/build.gradle.kts:115`) despite all app icons being hand-drawn. That library is roughly 2–3 MB of bytecode and is unused. **VERIFIED** (no `Icons.` usage found).

**Second weakness:** 1.8 dp stroke against a 1.8 dp grid means small icons (16 dp in the selection bar) lose a visible stroke at 1× density. **UNVERIFIED** — needs a physical screen.

### 6.4 Spacing and components (`HgTheme.kt:84-98`)

`gutter 20`, `gridGap 3`, `sectionGap 24`, `cardGap 12`, `minTouch 48`, `toolbarHeight 56`, `bottomBarHeight 64`. Radii: tile 10, card 16, sheet 28, chip 12, pill 26.

Reusable components: `HgScaffold`, `HgToolbar`, `HgScreenTitle`, `HgIconButton`, `HgChip`, `HgSelectionHeader`, `HgSelectionActions`, `HgDeleteDialog`, `MediaThumbnail`, `FavouriteBadge`, `SelectionBadge`, `EmptyResults`, `SearchChipsRow`.

**Strength:** this is a real design system, not a style guide. Token changes propagate.

**Weakness:** there is no `HgButton` for primary actions and no `HgAvatar`/`HgSectionHeader`; three screens each re-implement a section header locally.

### 6.5 Theming infrastructure

`values/`, `values-night/`, `values-v31/` (splash only) — correct separation. The launch window cannot read stored preferences, so the splash background is duplicated in `values-night` rather than being theme-driven. **VERIFIED** — this is a platform constraint, documented.

## 7. Architecture & Technical Quality

### 7.1 Shape

```
MainActivity (FragmentActivity, edge-to-edge)
└── HGalleryApp            hand-written state machine, no nav graph
    ├── tab state          4 siblings
    ├── overlay state      album / custom album / search / settings / trash / viewer / player
    └── AppContainer       manual DI, one instance, application-scoped
        ├── MediaStore     StateFlow<List<MediaItem>>, the single source of truth
        ├── ThumbnailStore bounded LruCache
        ├── SettingsRepository  DataStore
        ├── CustomAlbumStore / TrashStore  DataStore
        ├── ExifReader     on-demand, IO dispatcher
        └── MediaActions / MediaRepository / PlayerController
```

`core/` holds 21 platform-free files: grouping, filtering, framing, ordering, policies, formatting, and the Persian calendar. Every rule worth testing lives there and is tested with plain JVM tests.

**This is the strongest part of the project.** The separation is real: `core` has no Android imports at all, so its 138 unit tests run without an emulator.

### 7.2 State management

Plain `mutableStateOf` inside composables plus `StateFlow` in the data layer. **No ViewModel is used anywhere**, despite `lifecycle-viewmodel-compose` being declared.

**Consequence — a real defect:** all UI state (which tab, which album, viewer id, selection) lives in `remember { }` inside `HGalleryApp`. On configuration change the activity is declared with `configChanges="orientation|screenSize|screenLayout|keyboardHidden|uiMode"` (`AndroidManifest.xml:35`), so the activity is **not** recreated and state survives rotation. But it does **not** survive process death, and nothing is `rememberSaveable`. **PARTIALLY VERIFIED** — rotation survives by manifest, not by design.

### 7.3 MediaStore integration (`data/MediaRepository.kt:39-110`)

One query over `MediaStore.Files` filtered to images and videos, ordered `DATE_TAKEN DESC, _ID DESC`. All metadata is normalised into `MediaItem` at load time, with `DATE_ADDED` as a fallback when `DATE_TAKEN` is 0.

**Strength:** one pass, one list, and every screen derives from it — albums, highlights, discover, search, the video queue. There is no second source of truth to drift.

**Weakness (scale):** the whole library is held in memory as `List<MediaItem>`. At 12,237 LOC's own estimate of ~20,000 items this is roughly 20,000 × ~200 bytes ≈ 4 MB of objects plus string data, and one cursor pass. It works; it is not free. **UNVERIFIED at scale** — fixtures are 10 items.

**Weakness (correctness):** `_ID DESC` as the tiebreaker means two photos with the same second can reorder between loads only if the platform renumbers ids; in practice stable. Fine.

### 7.4 Caching (`data/Thumbnails.kt`)

`LruCache<String, Bitmap>` sized `min(heap/4, 48 MiB)`, `sizeOf` = `allocationByteCount`, cells requested at 256 px. `invalidate()` drops keys by URI. Platform thumbnail cache does the disk work.

**Strength:** correct budget, correct `sizeOf`, and an explicit invalidation path used after delete and rotate.

**Weakness:** the key includes `cellPx` and `isVideo` but **not** the orientation, so a rotated photo can serve a stale bitmap until the LRU evicts it — except `MediaStore.rotate()` calls `thumbnails.invalidate()` (`MediaStore.kt:195`), so this is handled. Good.

**Weakness:** no `Bitmap.Config` control on the API 29+ path — `loadThumbnail` returns `ARGB_8888`, twice the bytes of the `RGB_565` used on the legacy path. On a 48 MiB budget that halves the number of cached cells. **VERIFIED by reading `decode()` at `:63-86`.**

### 7.5 The viewer's image memory — the likely cause of the reported slowness

`ui/viewer/FullResolutionImage.kt:29-45`:

- decodes at `maxEdge = 2048`, `ARGB_8888` → up to 2048 × 2048 × 4 ≈ **16 MB per image**;
- `HorizontalPager` with `beyondViewportPageCount = 1` (`ViewerScreen.kt:152-153`) keeps **three** pages composed;
- there is **no cache** — every recomposition of a page re-runs `LaunchedEffect(item.id)` only on id change, so revisiting a page re-decodes from scratch.

So the steady state is up to **48 MB of bitmaps** held by the viewer, on top of a 48 MiB thumbnail LRU, plus the ExoPlayer buffers if a video was ever opened. On a 3 GB device this is survivable; on a 2 GB device it is close to the limit, and it is the most likely reason the app feels slow when paging quickly. **UNVERIFIED as a measurement** — I have not profiled it, and I will not claim a number I did not observe.

The concrete inefficiencies, in order:

1. **No down-scale to the display size.** 2048 px is chosen as a constant, not from the view size. On a 1080×2400 screen a portrait photo is displayed at ~1080 px wide; 2048 wastes ~3.6× the bytes.
2. **No decode-result cache.** Swiping back re-decodes.
3. **No `inPreferredConfig` choice.** `RGB_565` would halve the bytes for photos, at a cost in gradients.
4. **`beyondViewportPageCount = 1`** decodes neighbours before they are needed — good for latency, bad for memory.

### 7.6 Background work

None. There is no `WorkManager`, no `Service`, no `CoroutineWorker`. Loading is a suspend function called from a `LaunchedEffect`; EXIF reads are on `Dispatchers.IO`; thumbnail decodes are on `Dispatchers.IO`.

**Consequence:** duplicate detection (`core/SimilarityDetector.kt`) has an algorithm, tests, and **no caller**. It cannot run without a worker. **VERIFIED.**

### 7.7 Lifecycle and memory

- `PlayerController` is released in `DisposableEffect` — correct, and the reason for the §4.1 bug is not a leak but a stale reference.
- `ThumbnailStore` is application-scoped and never cleared on `onTrimMemory`. **UNVERIFIED** whether this matters; there is no trim callback registered anywhere.
- Bitmaps in the viewer are released when the page leaves composition, because `beyondViewportPageCount` bounds it. No explicit `recycle()`, which is correct for Compose.

### 7.8 Battery

Video playback holds no wake lock and no foreground service, which means **audio will stop if the app is backgrounded** — acceptable, and the reason the "background playback" item in §4.4 is architectural rather than cosmetic.

### 7.9 Accessibility

79 `contentDescription`/`semantics` usages across 54 UI files. Merge semantics are used on grid cells so TalkBack reads one label per tile. `Role.Tab` and `Role.Button` are set. Disabled controls are labelled.

### 7.10 Privacy and offline

- No `INTERNET` permission. **VERIFIED.**
- `allowBackup="false"`, `dataExtractionRules` present. **VERIFIED.**

## 11. Summary Judgement

The project is **structurally sound and functionally broader than it looks**: a real design-token system, a genuinely platform-free `core` with 138 passing tests, one MediaStore pass feeding five screens, correct scoped-storage handling, and a hard offline guarantee at the manifest level. The build is green end to end and produces a signed, installable APK.

It is **materially weaker in exactly the two places you named**: the viewer and the player. Both have zero automated tests; both contain defects that a test would have caught within a minute. The audio-without-picture bug is a stale-reference bug, not a Media3 limitation. The missing photo↔video swipe is two screens that should be one. The "slow" feeling is consistent with a viewer that never sizes its decodes to the screen and never caches them — but that is a hypothesis backed by code reading, **not a measurement**, and I will not dress it up as one until a benchmark runs on real hardware.

Nothing has ever run on the phone this app is for. Until it does, every performance claim — mine and the project's own — is provisional.
